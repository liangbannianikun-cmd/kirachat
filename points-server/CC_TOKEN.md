# CC 币发行与掉落设计

## 已锁定参数

- 最大供应量：`1,145,141,919,810 CC`
- 精度：18 位
- 初始供应量：0；部署不会提前把总量铸给部署者
- 转账：自由转账
- 增发：持有 `MINTER_ROLE` 的地址可以增发，但永远不能突破最大供应量
- 销毁：持币人可以销毁自己的币，也可以授权第三方代为销毁
- 暂停、冻结、黑名单：合约没有这些能力
- 名称和符号：部署参数；`CC_SYMBOL` 未最终确认前不得部署主网
- 官方图标：`../app/src/main/res/mipmap-nodpi/app_icon.png`；登记信息见
  `cc-token-info.json`

`CCCoin.sol` 使用 OpenZeppelin `ERC20Capped`、`ERC20Burnable` 和
`AccessControl`。正式环境的默认管理员应是多签钱包；发行服务器不能持有
默认管理员权限。

## 掉落曲线

以下“年”均从 `EMISSION_START_TIME` 开始计算：

| 发行年 | 年度掉落上限 |
| --- | ---: |
| 第 1 年 | 959,905 |
| 第 2 年 | 959,905 |
| 第 3 年 | 28,629 |
| 第 4 年 | 28,629 |
| 第 5 年 | 28,628 |
| 第 6 年 | 28,628 |
| 第 7–10 年 | 每年 8,964 |
| 第 11–14 年 | 每年 4,482 |
| 第 15–18 年 | 每年 2,241 |
| 以后 | 每四年减半一次 |

按完整颗数计算，整个掉落曲线约释放 `2,106,036 CC`，只占最大供应量约
`0.00018391%`。最大供应量中仍有约 `1,145,139,813,774 CC` 不属于掉落曲线，
可由其他持有 `MINTER_ROLE` 的发行用途铸造。

这意味着“总供应量”和“社区掉落量”相差极大。上线前必须公开说明剩余供应的
用途、锁仓和多签规则，否则即使掉落曲线公平，管理员仍拥有极强的稀释能力。

## 为什么使用周结算

客户端行为不会立即触发链上铸币。服务端每周完成风控后生成一个 Merkle
领取树，再把根和本周总额提交给 `CCEmissionDistributor`：

1. 每周总池固定，刷再多请求也不会增加发行量。
2. 合约按年度累计所有周额度，超过年度上限会直接回滚。
3. 周根必须在该周结束后的 28 天内发布，不能多年后补发旧额度。
4. 每周 Merkle 根发布后不可修改。
5. 领取累计值不能超过发布根时申报的周总额。
6. 每个钱包每周只能领取一次。
7. 任何人都可以代付领取交易，但代币只能发到叶子中写明的钱包。
8. 没通过风控或无人领取的额度不会自动铸造。

## 防机器人评分

默认策略位于 `src/drop/scoring.mjs`。钱包必须同时满足：

- 钱包签名验证通过，证明用户控制领取地址。
- 账号至少存在 14 天，钱包至少绑定 7 天。
- 一周至少 3 个活跃日；不按消息条数直接奖励。
- 设备通过 Play Integrity，或通过单独的人工身份验证。
- 同一设备最多关联 2 个账号。
- 设备近期请求量不能处于异常高频状态。
- 风险分不高于 49，封禁账号没有资格。

得分只计算有上限的行为：

- 活跃日：最多 5 天，每天 10 分。
- 有效会话：最多 6 次，每次 8 分。
- 被采纳的角色卡、世界书或社区贡献：最多 2 次，每次 60 分。
- 被确认有帮助的举报：最多 2 次，每次 20 分。
- 连续活跃：最多 4 周，每周 5 分。

“有效会话”应由服务端定义为持续一定时间、包含真实模型成功响应且文本不重复的
会话。同一账号短时间重复提交相似内容只能算一次。

最终使用平方根权重降低头部优势，并执行：

- 单钱包最多获得当周池的 `0.00001`，即 `0.001%`。
- 同设备、同资金来源或其他强关联集群合计最多获得当周池的 3%。
- 合格账户少于 100 个时不生成掉落根。
- 风险事件至少延迟一周结算，代币领取前完成封禁和人工复核。

在 `0.00001` 的单钱包上限下，理论上至少需要 100,000 个达到上限的独立合格钱包，
才能分完一整个周奖池。人数不足时，剩余部分保持未发行，不会重新集中分配给其他钱包。

Play Integrity 只是一个信号，不能单独证明“一个真人”。服务端还应结合设备召回、
钱包资金来源、IP/ASN 速率、行为相似度和人工复核。不得把原始聊天内容写入
区块链或掉落文件。

## 生成周度 Merkle 根

复制 `drop-input.example.json`，填入经过服务端聚合和脱敏的账户指标。金额使用
最小单位；例如 `1000 CC` 是 `1000000000000000000000`：

```powershell
npm.cmd run drop:build -- .\drop-input.json .\drop-output.json
```

输出文件包含 `merkleRoot`、`totalAllocation` 及每个钱包的证明。发布前需要：

1. 二人复核输入人数、拒绝原因和总额度。
2. 确认 `totalAllocation` 不超过当前发行年的剩余额度。
3. 将 `merkleRoot` 和 `totalAllocation` 提交给 `publishEpoch`。
4. 将每个钱包自己的领取证明通过认证接口返回，不公开整份风控输入。

## 部署

先安装依赖并运行测试：

```powershell
Set-Location .\points-server
npm.cmd install
npm.cmd test
npm.cmd run build
```

在 Base Sepolia 部署：

```powershell
$env:RPC_URL = "你的 Base Sepolia RPC"
$env:EXPECTED_CHAIN_ID = "84532"
$env:DEPLOYER_PRIVATE_KEY = "0x部署钱包私钥"
$env:CC_NAME = "CC Coin"
$env:CC_SYMBOL = "最终符号"
$env:EMISSION_START_TIME = "Unix秒级时间戳"
$env:ROOT_PUBLISHER_ADDRESS = "0x周度根发布钱包"
$env:FINAL_ADMIN_ADDRESS = "0x多签管理员"
$env:RENOUNCE_DEPLOYER = "false"
npm.cmd run deploy:cc
```

第一次部署必须保留部署者权限。确认多签能调用两个合约、发布者权限正确、
掉落合约拥有 `MINTER_ROLE` 后，才可以在下一次受控操作中撤销部署者权限。
不得未经验证直接设置 `RENOUNCE_DEPLOYER=true`。

测试网至少完成：

- 自由转账与持币人销毁。
- 非授权地址无法增发。
- 最大供应量无法突破。
- 超年度预算的根无法发布。
- 重复领取和伪造证明失败。
- 多签权限恢复演练。
- Merkle 生成脚本与合约叶子格式一致。

主网部署前还需要独立合约审计、代币分配与锁仓方案、隐私评估和适用地区的法律评估。
